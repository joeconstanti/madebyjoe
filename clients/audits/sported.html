    Launch dependency · Migration

    Keep existing journeys reachable

    Visitors following old links reach the right content, and search engines get a consistent set of destinations to crawl.

    Change and success checks
    Change
    Keep useful URLs where practical. Map every changed path to a relevant destination, update internal links, and generate the release sitemap from canonical, indexable pages. Review the legacy news, tags and regional archives before consolidating them.
    How to prove it
    Check all 428 recorded routes against an approved disposition. Test changed routes for a single permanent redirect to the intended destination and check every release sitemap entry for a 200 response.

    Google Search Central migration guidance

    High · Findability

    Give every priority page a clear purpose

    People can recognise the right page in search, understand it on arrival and distinguish nearby links. Editors get a repeatable way to publish complete pages.

    Change and success checks
    Change
    Build page-type defaults for titles, descriptions, primary headings and breadcrumbs. Write explicit titles and intros for Get Support, Grant Giving, Current Programmes and the main impact pages. Give programme cards and news links descriptive labels.
    How to prove it
    Crawl the indexable launch inventory for a primary heading, meaningful title, description and self-canonical. Review the priority landing pages for clarity and validate retained structured data from rendered HTML.
    High · Club journeys

    Make funding opportunities easier to act on

    Club visitors currently move between Get Support, Grant Giving, Current Programmes and external application destinations.

    Clubs can tell whether a programme fits them and whether they can apply. Editors can update a deadline or close a round in one place.

    Change and success checks
    Change
    Use one programme model with status, eligibility, geography, deadline, contact and application URL. Show open opportunities first. Give closed and completed programmes a clear state and retain useful impact evidence.
    How to prove it
    Have representative users find an open fund, check eligibility and reach its application link on a phone. Verify each published programme has an owner, visible status and a working next action.
    High · Mobile performance

    Reduce the work required to show the page

    Visitors on slower connections can see the page sooner. Stable media dimensions keep the navigation and application buttons from moving during load.

    Change and success checks
    Change
    Serve appropriately sized hero images, reserve image dimensions, load scripts only where used and choose a staging host with compression and caching. Replace shared WordPress and Elementor runtime dependencies template by template as their behaviour is covered.
    How to prove it
    Repeat three cold Lighthouse runs per key route and device with the same settings on a comparable host. Compare median LCP, CLS, blocking time, transfer and requests. Monitor field LCP, INP and CLS where data is available.

    Core Web Vitals measurement guidance

    Launch dependency · Services

    Keep forms and downloads usable

    Visitors can complete important actions, and staff can see where data goes and who owns each service. Reliable document links preserve access to policies and evidence.

    Change and success checks
    Change
    Confirm destinations for newsletter signup, legacy volunteer forms and Times Appeal. Keep the existing application, Hub and donation handoffs. Recover missing governance and research PDFs or agree replacement destinations with Sported.
    How to prove it
    Check all approved handoff URLs and document links. Use approved test submissions to verify validation, confirmation and downstream receipt, and record an agreed fallback for any integration that cannot move at launch.
    High · Accessibility and maintenance

    Build reusable, testable templates

    The parity build reproduces captured WordPress output. The next phase can give programmes, news, case studies and governance content their own structured templates.

    Keyboard and screen-reader users get a predictable experience, and a template fix can improve many pages at once. Structured content reduces reliance on manual page layouts.

    Change and success checks
    Change
    Use shared components for navigation, cards, forms and responsive media. Establish accessible focus order, visible labels and error states. Give editors required fields and a preview for each content type before selecting a long-term CMS.
    How to prove it
    Test the menu and key journeys with keyboard navigation, screen-reader spot checks and a narrow viewport. Ask an editor to create and update a programme in the proposed workflow before committing to the CMS.
    Measure after launch

    Once account access and consent are in place, establish baselines for organic landing pages, indexed URLs and priority journey events. Monitor 404s, programme application clicks, member Hub handoffs and newsletter confirmations. Compare equivalent periods and record changes in campaigns or seasonality before interpreting the results.

    Coverage & limits

    Method and evidence
    • Built HTML, frozen route manifest and public XML sitemap snapshot.
    • Lighthouse Chrome runs on the public baseline and loopback build. One run per page and device.
    • Local asset bytes include directly referenced staged files. Browser-selected responsive images, dynamic chunks, cache and compression vary by run.
    • Structured data is counted by declared type. Search result eligibility and content accuracy were outside this check.
    Measurement limits and launch checks

    CrUX field data, Search Console index coverage, analytics and production form submissions remain unverified. Local preview sends a noindex header. Review the production robots policy before release.
